# CD Store v12.0

هذا التحديث يغيّر نظام العملات عند الزبون بالكامل، مع بقاء الحسابات الداخلية والشبكية آمنة ومتوافقة مع الإصدارات السابقة.

## 1) الزبون يختار عملة حسابه

عند أول استخدام أو من زر **💱 العملة** يختار الزبون واحدة من:

- 💵 الدولار `USD`
- 🇮🇶 الدينار العراقي `IQD`
- 🇪🇬 الجنيه المصري `EGP`

الاختيار محفوظ لكل مستخدم ويمكن تغييره لاحقاً.

## 2) كل واجهة الزبون تتحول إلى العملة المختارة

إذا اختار الزبون IQD، تظهر له بالدينار العراقي:

- أسعار المنتجات
- رصيد المحفظة
- سعر الطلب
- المبلغ الناقص لإكمال الطلب
- سجل الطلب وتفاصيله
- مكافآت الإحالة
- إشعارات الشحن والموافقة
- طرق الدفع العراقية

ونفس الشيء للـ EGP أو USD.

### مثال

إذا سعر المنتج الداخلي هو `$1` وسعر العرض العراقي هو `1$ = 1500 IQD`، الزبون الذي اختار IQD يشوف:

`1,500 دينار عراقي`

ولا يحتاج يشوف `$1` في واجهة الشراء العادية.

## 3) Binance هو الاستثناء الوحيد

Binance يبقى دائماً **USDT/USD** بغض النظر عن عملة الزبون.

مثال:

- الزبون مختار IQD.
- يشحن `1 USDT` عبر Binance.
- التحقق من Binance يبقى بالدولار/USDT.
- بعد نجاح التحقق، محفظته تظهر `1,500 دينار عراقي` إذا السعر 1500.

إذا غيّر عملته لاحقاً إلى EGP، نفس القيمة تتحول للعرض بالجنيه المصري بدون خسارة الرصيد.

## 4) المحفظة الداخلية عالية الدقة

حتى لا تضيع مبالغ مثل `1000 IQD` بسبب تقريب السنتات، النظام يحتفظ بالقيمة داخلياً بدقة USD عالية (`8` منازل عشرية)، بينما الزبون لا يرى إلا العملة التي اختارها.

تمت ترقية دقة:

- `Users.balance`
- `BalanceTransactions.amount`
- `PurchaseOrders.walletApplied`
- `PurchaseOrders.externalAmount`
- `NetworkSharedPaymentRequests.amountUsd`

المهاجرات تعمل تلقائياً عند التشغيل ولا تحتاج حذف قاعدة البيانات.

## 5) كل طرق الدفع العادية تظهر عند جميع البوتات

طرق الدفع المضافة من لوحة الإدارة أصبحت مشتركة فعلياً بين كل أعضاء الشبكة.

مثال:

- أحمد يضيف `Vodafone Cash` بعملة EGP.
- الطريقة تظهر تلقائياً في بوت نبيل ورضا وباقي الشركاء عند اختيار EGP.
- نبيل يضيف طريقة عراقية IQD.
- الطريقة تظهر تلقائياً في بوت أحمد وباقي الشركاء عند اختيار IQD.

كل طريقة يظهر معها صاحبها حتى لا تختلط الطرق المتشابهة.

## 6) الموافقة تذهب لصاحب المحفظة الحقيقي

إذا زبون داخل بوت نبيل استخدم Vodafone Cash التابعة لأحمد:

1. الزبون يرسل الإيصال داخل بوت نبيل.
2. الطلب الشبكي يذهب إلى بوت أحمد.
3. أدمن أحمد يرى اسم الطريقة، الزبون، المتجر الذي بدأت منه العملية، والمبلغ بالجنيه المصري.
4. أحمد يضغط **✅ وصل المبلغ** أو **❌ ما وصل**.
5. إذا وافق، بوت نبيل يشحن رصيد الزبون أو يكمل الطلب تلقائياً.
6. الحساب بين أصحاب البوتات يسجل داخلياً بالدولار حتى تبقى الديون والتسويات دقيقة.

والعكس صحيح لأي طريقة يضيفها نبيل أو رضا أو أي شريك آخر.

## 7) ترتيب طرق الدفع

إذا اختار الزبون IQD:

- Binance — USDT
- طرق الدفع العراقية لكل الشبكة

إذا اختار EGP:

- Binance — USDT
- طرق الدفع المصرية لكل الشبكة

إذا اختار USD:

- Binance
- كل طرق الدفع العادية بعملة USD الموجودة في الشبكة

Binance يبقى خاصاً بالبوت نفسه، وإذا Client لم يضف Binance محلياً يبقى fallback الرئيسي كما في النسخ السابقة.

## 8) أسعار التحويل

من إعدادات الإدارة أصبح ممكناً تعديل **سعر IQD وسعر EGP معاً** في أي بوت، لأن زبائن نفس البوت يمكنهم اختيار أي عملة.

الافتراضات الحالية عند عدم التعديل:

- `1 USD = 1500 IQD`
- `1 USD = 50 EGP`

ويمكن تغييرهما من لوحة الإدارة.

## 9) إصلاح Railway السابق موجود داخل هذه النسخة

v12.0 مبني فوق إصلاح v11.9.1، لذلك مشكلة:

`column "submittedOrderId" does not exist`

مصلحة. الأعمدة تضاف أولاً ثم يتم إنشاء الـIndexes، فلا تحتاج إلى تطبيق ملف الإصلاح القديم فوق v12.0.

## 10) الديون بين أصحاب البوتات

لا تتغير قاعدة الديون:

- الديون والتسويات بين أصحاب البوتات تبقى USD.
- تسوية الدين عبر Binance تبقى USDT.
- Order ID يتم التحقق منه تلقائياً بواسطة Binance الخاص بالطرف المستلم عندما تكون Binance API متاحة.

## النشر

يجب تحديث **Master وكل Client bots** إلى v12.0 حتى تكون واجهة العملات وطرق الدفع المشتركة متطابقة عند الجميع.

لا تحتاج حذف PostgreSQL ولا إنشاء قاعدة بيانات جديدة.

بعد رفع الملفات شغّل:

```bash
npm run check
```

ثم Redeploy لكل Service على Railway.


# تحديث v12.0.2 — إصلاح ظهور محافظ الشركاء عند الجميع

هذا التحديث يعالج حالة أن شريكاً مثل أحمد يضيف Vodafone Cash بالجنيه المصري داخل بوت أحمد، لكن الطريقة لا تظهر في بوت نبيل أو بقية الشركاء.

## السلوك بعد الإصلاح

- إذا الزبون اختار **EGP**: يظهر **Binance — USDT** ثم كل طرق الدفع المصرية الفعالة من جميع الشركاء، مثل Vodafone Cash الخاصة بأحمد.
- إذا الزبون اختار **IQD**: يظهر **Binance — USDT** ثم كل طرق الدفع العراقية الفعالة من جميع الشركاء.
- إذا الزبون اختار **USD**: يظهر Binance وكل طرق الدفع العادية بالدولار.
- اسم صاحب المحفظة يبقى ظاهر مع الطريقة حتى تعرف لأي شريك تعود.
- إذا الزبون استخدم محفظة أحمد داخل بوت نبيل، طلب الموافقة يذهب إلى أحمد؛ الرصيد/الطلب لا يكتمل إلا بعد موافقة صاحب المحفظة.

## شنو تغير تقنياً؟

1. كل Client يرسل **Snapshot كامل** لمحافظه المحلية إلى Master بدلاً من الاعتماد فقط على مزامنة طريقة واحدة كل مرة.
2. Master يقوم أيضاً باكتشاف طرق الدفع مباشرة من Schemas الشركاء الموجودة في نفس PostgreSQL (best-effort)، لذلك حتى إذا فشلت مزامنة قديمة تبقى المحافظ قابلة للاكتشاف.
3. حذف/إيقاف طريقة دفع ينعكس على السجل المشترك، حتى لا تبقى طريقة قديمة ظاهرة.
4. بقيت مزامنة الطريقة الواحدة القديمة كـ fallback للتوافق مع النسخ السابقة.

## مهم بالنشر

ارفع v12.0.2 أولاً على **Master**. بعد نجاحه، حدّث Clients أيضاً حتى يستخدمون Snapshot sync الجديد.
لا تحذف PostgreSQL ولا أي بيانات.

## v12.2.0 — حماية البيانات عند التحديث

هذا الإصدار يجعل تشغيل البوت والتحديثات غير هدامة للبيانات المخزنة في PostgreSQL:

- لم يعد بدء البوت يعيد بناء `Merchant.description` ويحذف الحقول الإضافية. يتم الاحتفاظ بـ Premium Emoji IDs وRich Text وبيانات `تنفيذ خدمة` وأي حقول مستقبلية غير معروفة للإصدار.
- لم يعد بدء البوت يحذف مخزوناً أو صفوفاً مكررة تلقائياً. يتم فقط تعبئة `fingerprint` المفقود إذا كانت البيانات صالحة، بدون حذف أو تعديل محتوى المخزون.
- Migration التوافق القديم أصبح يعمل مرة واحدة فقط ويسجل علامة في جدول `Settings`، بدل أن يعاد تنفيذه في كل تشغيل.
- Premium Emoji IDs الأساسية للواجهة يتم حفظها في `Settings` داخل PostgreSQL عند أول تشغيل ثم تحميلها من قاعدة البيانات في كل إصدار لاحق، لذلك تحديث ملفات الكود لا يعيدها إلى قيمة hard-coded جديدة.
- طرق الدفع وCustom Emoji الخاصة بها تبقى في `PaymentMethods`، والمنتجات والمستخدمون والأرصدة والطلبات والإعدادات تبقى في جداول PostgreSQL ولا يتم استبدالها أثناء التحديث.
- `sequelize.sync({ alter: false })` مستمر؛ التحديثات تضيف الأعمدة المطلوبة فقط عن طريق migrations متوافقة، ولا تعمل Reset للجداول.

### مهم على Railway
حتى تبقى البيانات نفسها يجب عدم حذف خدمة PostgreSQL أو تغيير `DATABASE_URL`/`DATABASE_SCHEMA` إلى قاعدة أو Schema جديد. تحديث الكود أو Redeploy وحده لا يمسح البيانات.

## v12.4.0 — تحسين السرعة والاستجابة في كامل البوت

- إضافة Cache داخلي لإعدادات PostgreSQL حتى لا ينفذ البوت استعلام قاعدة بيانات لكل زر/رسالة على نفس الإعداد.
- Cache آمن لإعدادات Binance المشفرة مع تحديث فوري عند أي تغيير من لوحة الإدارة.
- Cache للتحقق من اشتراك القناة: العضو المؤكد لا يحتاج استدعاء Telegram `getChatMember` مع كل ضغطة زر. زر التحقق اليدوي يبقى Force Refresh.
- استبدال `findOrCreate` للمستخدم الموجود بمسار Primary Key أسرع، مع حماية Race لأول رسالة من المستخدم الجديد.
- تحويل عدّ مخزون قائمة المنتجات من N استعلامات إلى استعلام تجميعي واحد Batch.
- نفس تحسين المخزون مطبق على لوحة إدارة المنتجات وقائمة إضافة المخزون وCatalog الـMaster.
- Client catalog sync صار بمدة Cache قصيرة + in-flight de-duplication: إذا ضغط عدة مستخدمين بنفس الوقت لا يرسل كل واحد طلب Catalog جديد للـMaster.
- Catalog sync نفسه صار Bulk Upsert بدلاً من `findOne + update` لكل منتج.
- Shared payment methods صار لها Cache قصير، مع stale fallback عند تعطل الشبكة مؤقتاً.
- Master لم يعد يفحص Schemas كل مرة يفتح مستخدم شاشة الدفع؛ Schema discovery صار throttled ويعمل مرة كل فترة قصيرة فقط.
- مزامنة المحافظ المشتركة المتطابقة لا تعاد كل 30 ثانية؛ يتم الإرسال عند التغيير مع heartbeat دوري للإصلاح الذاتي.
- Network background watcher صار يمنع تداخل دورة جديدة إذا الدورة السابقة ما خلصت، لمنع تراكم عشرات عمليات الشبكة/DB على Railway.
- إضافة Cache لأسماء/عملات المتاجر بالشبكة لتقليل استعلامات `NetworkClients`.
- تقليل timeout لقراءات الشبكة حتى فشل Master لا يعلق زر العميل 20 ثانية.
- إضافة Indexes غير هدامة لمسارات الطلبات والمدفوعات والمنتجات الشائعة.
- كل الـCaches مؤقتة فقط بالذاكرة؛ مصدر الحقيقة يبقى PostgreSQL، لذلك ماكو فقدان بيانات أو تغيير في الحسابات/الدفع.
- نظام الدفع، الرصيد، التسوية، تنفيذ الخدمة، الشبكة والمخزون ما تغيرت قواعدها المالية.

### قيم الأداء الافتراضية
- Settings cache: 60 ثانية.
- Secure settings cache: 30 ثانية.
- Channel membership: 5 دقائق للمشترك / 20 ثانية لغير المشترك.
- Catalog cache: 12 ثانية.
- Shared payment methods: 12 ثانية.
- Master schema discovery: 30 ثانية.

يمكن تعديلها لاحقاً من ENV إذا احتجنا، لكن القيم الافتراضية مناسبة لـ Railway وبوتات المتجر الحالية.

إضافات أداء مكملة في نفس النسخة:
- Cache لمصادقة Clients على Master حتى لا ينفذ Query على NetworkClients مع كل API request.
- Cache قصير لـ Master catalog snapshot لتجميع طلبات عدة Clients بنفس اللحظة.
- Cache لخيارات الدفع الموروثة من Master بدل طلب HTTP جديد بكل شاشة دفع.
- رفع حد الضغط الطبيعي على الأزرار من 12 إلى 30 عملية/10 ثوانٍ للمستخدم و60 للأدمن، حتى التنقل السريع ما يبان كأنه أزرار ميتة.
- إضافة المخزون المحلي والمشترك صار Batch: فحص التكرار باستعلام واحد وحفظ دفعة واحدة بدل find/create لكل سطر.
- أي إنشاء/تعديل/حذف/إضافة مخزون/تسليم شبكي يبطل Catalog cache تلقائياً حتى السرعة ما تسبب بيانات قديمة مدة طويلة.

## v12.5.2 — فصل السعر عن المخزون وحد الشحن الأدنى

- تم عزل السعر ورقم المخزون بصرياً داخل أزرار المنتجات حتى لا يندمجان أو ينعكس ترتيبهما في واجهة Telegram العربية RTL.
- كل شحن عبر محفظة غير Binance صار حده الأدنى ما يعادل 1 USD حسب سعر صرف العملة الحالية.
- إذا كان الأدمن محدد حد أدنى أعلى من قيمة 1 USD، يبقى الحد الأعلى محفوظاً.
- Binance يبقى بحد أدنى 0.01 USDT (أو قيمة BINANCE_MIN_AMOUNT إن كانت أعلى).
- رسائل إدخال مبلغ الشحن أصبحت أوضح وتعرض الحد الأدنى بصيغة منفصلة، مثل: `الحد الأدنى: 1,500 دينار عراقي`.


## v12.5.3 — إصلاح المنتج الحر متعدد الأسطر
- المنتج الحر صار محمياً بطبقتين: كل رسالة Telegram كاملة = قطعة مخزون واحدة مهما كان عدد الأسطر.
- فحص التكرار للمنتج الحر صار على الرسالة الكاملة فقط، وليس على كل سطر داخلها.
- تمت إضافة بصمة `free-message-v2` حتى لا تختلط بصمات الرسائل الكاملة مع أي بصمات قديمة ناتجة من سلوك سابق.
- إذا كانت الرسالة تحتوي إيميل + باسورد + رمز مصادقة + رابط في 8 أسطر، النتيجة تكون `تمت إضافة: 1` وليس 8 منتجات.


## v12.5.4 — ترتيب المنتجات حسب المخزون والاسم

- المنتجات التي مخزونها أكبر من صفر تظهر أولاً، والمنتجات الفارغة تنزل إلى أسفل القائمة.
- المنتجات المتشابهة بالاسم تُجمع بجانب بعضها داخل نفس مجموعة المخزون؛ مثال: `جيميني شهري` ثم `جيميني 3 شهور` ثم `جيميني 18 شهر`.
- خوارزمية التجميع تتجاهل الكلمات العامة مثل: برو، حساب، مفعل، مشترك، ضمان، شهر/شهور، والأرقام؛ لذلك تتعرف على اسم العائلة الأساسي للمنتج.
- داخل نفس العائلة يُحافظ على ترتيب الإنشاء/الترتيب الأصلي، حتى المنتج الذي أُضيف أولاً يبقى قبل النسخة التي أُضيفت بعده.
- نفس الترتيب يطبق على قائمة الزبون، إدارة المنتجات، وقائمة إضافة المخزون.
- لا يوجد أي تغيير على كميات المخزون أو آلية البيع نفسها؛ التعديل خاص بترتيب العرض فقط.


## v12.6.0 — سعر محلي لكل بوت وربح فرق السعر

- سعر صاحب المنتج في الكتالوج الشبكي أصبح الحد الأدنى للبيع في باقي البوتات.
- صاحب أي بوت شريك يقدر يرفع سعر منتج مضاف من متجر آخر، والتعديل يبقى داخل Schema/Bot الخاص به فقط.
- لا يمكن خفض السعر المحلي تحت سعر صاحب المنتج.
- إذا رجع الشريك السعر إلى السعر الأساسي، يُلغى الـ override ويرجع نظام عمولة 10% الاعتيادي.
- إذا رفع الشريك السعر، لا تُحسب عمولة 10% على ذلك البيع: صاحب المخزون يأخذ قيمة مساهمته المسجلة، والبوت البائع يحتفظ بفرق السعر كربح.
- مثال: مخزون قيمته $1، سعر بوت أحمد $3 => صاحب المخزون $1 وأحمد $2.
- رفع صاحب المنتج للسعر الأساسي يحدّث الحد الأدنى عند كل البوتات؛ أي override صار أقل من الحد الجديد يُلغى تلقائياً.
- أضيف حفظ دائم للحقلين `networkBasePriceUsd` و `localPriceOverrideUsd` داخل PostgreSQL بدون حذف البيانات القديمة.


## v12.7.1 — ربح ثابت للأرقام + محاسبة عادلة للشركاء

- تسعير الأرقام الافتراضية أصبح آمناً من الخسارة:
  - تكلفة المزود حتى `$0.03` => سعر البيع `$0.30`.
  - أكبر من `$0.03` وأقل من `$0.30` => سعر البيع `$0.50`.
  - من `$0.30` وفوق => سعر البيع = تكلفة المزود + `$0.30` ربح ثابت.
  - أمثلة: `$0.30 -> $0.60`، `$0.80 -> $1.10`، `$1 -> $1.30`، `$2 -> $2.30`.
- شراء الرقم من بوت شريك (أحمد/رضا/أي Client) يسجل على ذلك المتجر ديناً للـMaster **بقيمة تكلفة المزود الحقيقية فقط**، وليس بسعر البيع.
- فرق سعر البيع عن تكلفة المزود يبقى ربحاً لصاحب البوت الذي تمت منه عملية البيع.
- نظام محاسبة طرق الدفع الموجود سابقاً يستمر كما هو ويعمل مع هذه التكلفة بالصافي:
  - إذا الزبون شحن من محفظة تخص نفس الشريك، لا يوجد دين عند الشحن؛ عند شراء رقم يصبح على الشريك فقط تكلفة المزود.
  - إذا الشحن دخل إلى محفظة Master أو شريك آخر، التزام استلام الأموال المسجل سابقاً يتقاص تلقائياً مع تكلفة الرقم، لذلك لا ينظلم أي طرف.
- عند إلغاء الرقم واسترجاع المزود للتكلفة، يتم عكس دين تكلفة المزود مرة واحدة فقط.
- أضيفت حالة محاسبية دائمة إلى `VirtualNumberOrders` مع Retry بالخلفية، حتى انقطاع Master مؤقتاً لا يضيع أي تكلفة بين المتاجر.
- عمليات المحاسبة Idempotent: إعادة المحاولة لا تضاعف الدين ولا الاسترداد.


## v12.8.0 — واجهة الأرقام الافتراضية متعددة اللغات

- عند فتح قسم شراء رقم افتراضي تظهر الخدمات المتوفرة مباشرة بدل إجبار المستخدم على البحث أولاً.
- أسماء الخدمات تظهر بالإنجليزية للمستخدم الإنجليزي، وبالعربية للمستخدم العربي مع أسماء عربية ثابتة للخدمات المعروفة وترجمة تلقائية للخدمات الأخرى عند الحاجة.
- بحث الخدمات يقبل الاسم العربي أو الإنجليزي أو رمز الخدمة.
- تمت إضافة بحث مستقل عن الدولة، ويقبل اسم الدولة بالعربية أو الإنجليزية.
- الدول تظهر مع علم الدولة، ويُعرض اسم الدولة بالعربية للمستخدم العربي وبالإنجليزية للمستخدم الإنجليزي.
- خيارات الدول/الأرقام مرتبة تصاعدياً من الأرخص إلى الأغلى، ثم حسب تكلفة المزود والاسم عند تساوي السعر.
- شاشة عرض السعر، تأكيد الشراء، والطلبات السابقة تستخدم نفس اللغة المختارة والأعلام.
- لا يوجد تعديل على قاعدة البيانات في هذا الإصدار.


## v12.8.2 — الخدمات المشهورة أولاً + Any number + فلترة التوفر

- واجهة شراء الرقم الافتراضي تعرض فقط الخدمات المشهورة والدارجة بالأولوية مثل Google/Gmail/YouTube وTelegram وWhatsApp وNetflix وInstagram وFacebook وTikTok وOpenAI/ChatGPT وApple وAmazon وغيرها.
- باقي الخدمات لا تملأ الصفحة الرئيسية؛ تبقى كلها متاحة من زر البحث بالعربي أو بالإنجليزي أو عبر رمز الخدمة.
- الخدمات التي لا تملك أي رقم متاح حالياً لا تظهر كأزرار شراء في الواجهة. يتم الاعتماد على ملخص `getPrices` العام لفلترة الخدمات قبل ضغط المستخدم.
- إذا بحث المستخدم عن خدمة غير موجودة أو موجودة لكن بدون توفر حالي، ينتقل البوت إلى خدمة SMSBower الرسمية `Any Other` ويعرضها للمستخدم باسم `أي رقم / Any number` مع الدول والأسعار المتوفرة.
- `أي رقم / Any number` يتم اكتشافها ديناميكياً من قائمة خدمات المزود، ولا يوجد API key أو رمز خدمة سري مثبت داخل الكود.
- الدول وخيارات السعر تبقى مرتبة من الأرخص إلى الأغلى، ولا تظهر الدول ذات count=0.
- إذا تغيّر التوفر بعد عرض الزر وقبل الشراء، لا يعرض البوت رسالة `ماكو أرقام متوفرة لهذا الاختيار حالياً`؛ يقوم بتحديث الخيارات تلقائياً والانتقال إلى الخيارات المتاحة/Any number عند الحاجة.
- أضيف Cache لملخص أسعار كل الخدمات لمدة قصيرة حتى تتم فلترة الواجهة بدون عشرات طلبات API عند كل دخول.
- لا يوجد تعديل على قاعدة البيانات في هذا الإصدار.
